# 工具结果的成败是类型化状态，不是文本前缀

> 状态：**accepted**（2026-10-07 随 `ToolRegistry` 拆分落地）。与渲染侧「块类型来自类型化事件」（ADR 0011 / 0017）是同一条规则，落在工具结果的成败上。

工具调用的成败过去只编码在回灌给模型的文本前缀里——`工具执行失败: ` / `🛡️ 策略拒绝: ` / `[HITL] 操作已被拒绝` / `[Hook 拦截 / PreToolUse]` / `MCP 工具返回错误` / `❌ …`——需要成败的消费方各自把它嗅回来。嗅的名单有两份，而且互相不一致：

| 名单 | 认作失败的前缀 |
|---|---|
| `isUsableMcpOutput`（StepSearch 回退；原在 `ToolRegistry`，现 `WebTools`） | `[HITL]` / `🛡️` / `工具执行失败` / `未知工具` / `MCP 工具返回错误` |
| `Agent.hookToolSucceeded`（收尾门的「成功」） | `工具执行失败` / `❌` / `执行命令失败` / `命令执行超时` |

前者不认 `❌`，后者不认 `🛡️` / `[HITL]`。两份都不认内置工具体自己返回的业务级失败——`写入文件失败: …` / `第1条 old_string 未找到…` / `文件不存在，请用 write_file 新建`——这些文案没有共同前缀，在文本上与成功无从区分。

## 证据

收尾门（ADR 0012 决策 4）在「本回合有成功写入、且写后没有成功的验证命令」时阻断收尾。按旧名单，下列**没有写成**的写类调用都被记成成功写入，收尾门因此要求一个什么都没写的回合先跑测试自证：

| 调用 | 回灌文本 | 旧判定 |
|---|---|---|
| `write_file` 写项目根外（策略拒绝） | `🛡️ 策略拒绝: 路径越界…` | 成功写入 |
| `write_file` 被 HITL 拒绝 | `[HITL] 操作已被拒绝：…` | 成功写入 |
| `write_file` 被 PreToolUse Hook 拦截 | `[Hook 拦截 / PreToolUse]\n…` | 成功写入 |
| `edit_file` 的 `old_string` 未命中 | `第1条 old_string 未找到…` | 成功写入 |
| `write_file` 落盘失败 | `写入文件失败: …` | 成功写入 |

`AgentFinishGateTest` 为前四行各钉一条用例；把旧的前缀名单放回 `hookToolSucceeded`，四条全红（被误阻断，多出第 3 次 LLM 调用）。

## 决策

1. **`ToolOutput` 带 `Status`**：`OK` / `ERROR` / `DENIED` / `BLOCKED` / `CANCELLED` / `TIMEOUT`，在**产生结果的地方**设置；消费方判断成败只读 `status()`，文本前缀只是给模型看的呈现。

   | 状态 | 谁设 |
   |---|---|
   | `CANCELLED` | 管线：执行前已取消 / 批次中断；工具体：用户取消 |
   | `ERROR` | 管线：未知工具、执行异常（`工具执行失败: `）；MCP `isError`；工具体的业务级失败（写 / 编辑失败、`old_string` 未找到、文件不存在、不支持的项目类型、快照恢复失败…） |
   | `DENIED` | 管线：`PolicyException`（`🛡️ 策略拒绝`）；HITL 拒绝 / 跳过；`web_fetch` 的网络策略 / 限流 |
   | `BLOCKED` | PreToolUse Hook `BLOCK` |
   | `TIMEOUT` | 批次超时；`execute_command` 的命令超时 |
   | `OK` | 其余 |

2. **`DENIED` 与 `BLOCKED` 分开。** 守卫拒绝与用户拒绝是 `DENIED`；Hook 的 `BLOCK` 是**模型反馈级**阻断（ADR 0012：原因回灌续跑），不是安全拒绝。合成一个值，消费方就会把质量门当安全事件处理。
3. **StepSearch 可用 = 有正文且状态不是 `ERROR` / `DENIED`。** `CANCELLED` / `BLOCKED` 算**可用**，原样回给模型：判成不可用就会回退去走真实网络搜索——用户刚取消、或 Hook 刚拦下，系统转身偷偷发一次网络请求。
4. **命令跑完、退出码非零是 `OK`。** `execute_command` 执行了就是 `OK`，退出码留在文本（`命令执行完成 (exit code: N)`），是命令的数据，不是工具的成败。需要退出码的消费方自己读（收尾门的验证判定）。
5. **其余不动。** 文本逐字节不变（模型看到的与之前完全相同）；业务级失败的审计仍记 `allow`（工具体正常返回；只有 `PolicyException` 记 policy-deny、异常记 `error`）；PostToolUse 对它们照常触发。状态是旁路新增的信息，不重新定义这两件事。

## 被否决的方案

- **业务级失败改抛异常**：异常会走 `工具执行失败: ` 前缀并记审计 `error`——模型看到的文本与审计结论同时改变，而这两者本次都不该动。
- **保留字符串、把两份名单修对**：同一个病。业务失败文案没有共同前缀，名单永远补不全；下一条新文案又会让名单再次分叉。
- **非零退出记 `ERROR`**：命令确实跑了；`grep` 无匹配退出 1、`diff` 有差异退出 1，都不是工具失败。把它们记成失败会让「跑了、结果是红的」与「没跑起来」混成一类。

## 后果

- **收尾门行为变化**：被拒绝 / 拦截 / 取消 / 业务失败的写类调用不再算成功写入，这类回合不再被要求自证；真实写入照旧被拦到验证为止。反方向也有一条：状态 `OK` 但正文以 `❌` / `工具执行失败` 等开头的结果（例如某个 MCP 工具正常返回、正文恰以 `❌` 开头）以前记失败、现在记成功——收尾门只看写类工具与 `execute_command`，不受影响；但 Stop payload 的 `turnToolSummary[].success` 会随之变化，经 `hooks.json` 接 Stop 的 shell Hook 看得到。
- **仍是字符串的**：`execute_command` 的「退出码为 0」由 `hookToolSucceeded` 读文本 `(exit code: 0)` 判定。只有这一个消费者，没有为它给 `ToolOutput` 加退出码字段。
- 判据：`ToolOutputStatusTest`（各产生点设的状态）+ `AgentFinishGateTest`（四条没写成的写类调用不触发收尾门）。
