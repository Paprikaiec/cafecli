# Java 21 虚拟线程 + 准入控制承载并发任务

[ADR 0005](0005-async-task-substrate-event-loop.md) 的 substrate 模型是"每个[[任务]]各跑各的、可自由阻塞等待、可大量并发"。在平台线程上这会出问题：前台 `spawn_agent` 在[[工具批次]]线程上**阻塞**等子任务，子任务又派生孙任务等更多线程——有界池被占满即**死锁**；且每条平台线程钉住 ~0.5–1 MB 栈，"上百并发 agent"在算对话历史成本前就先爆内存。项目当前编译目标 Java 17、无虚拟线程。

## 决策

1. **升级 Java 21**，每个任务及其阻塞等待跑在**虚拟线程**上（要求运行环境 JRE 21）。阻塞等待近乎免费，线程耗尽型死锁自然消解，内存压力回到对话历史本身（由 0005 的 LRU 回收 + 消息镜像上限治理）。
2. 仍设**全局准入控制**（虚拟线程不免除）：`深度上限`（硬兜底，限制 主→任务→子任务 派生层数）+ `等待即释放配额`（父任务前台等待子任务时释放自身准入名额）。两者都做——深度上限是硬底线，释放配额保活性。运行中任务受准入约束；空闲任务留存归 LRU 管，二者分离。

## 被否决的方案

- **留在 Java 17 + 有界平台线程池**：用深度上限或释放配额避免死锁、用池大小限并发。否决：承载"每任务一线程、自由等待、高并发"要持续与平台线程的栈成本和池占满风险搏斗，与 substrate 模型相悖；Java 21 LTS 已主流，作为脊柱底座值得。

## 后果

- 运行前提新增 **JRE 21**（`pom.xml` 编译目标与文档运行前提同步上调）。
- 准入上限取合理默认并可配置（对齐现有 `cafecli.*` 系统属性风格）。
- 准入控制需作为纯策略对象、与线程模型解耦，便于单测无死锁性（见 PRD 测试 seam）。
- 即便有虚拟线程，朴素信号量仍可能因"父持配额等子"而死锁——故准入必须**层级感知**（等待即释放），这是决策的硬约束而非可选优化。
