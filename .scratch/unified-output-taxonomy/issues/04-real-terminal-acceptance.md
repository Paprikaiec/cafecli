## Comments

### 第一轮真机人工验收，2026-09-01 —— 三个缺陷

用户在真实终端上跑完清单，**除下列三项外其余均正常**（含短终端那一档）。三项里只有第一项已修。

#### 1. 亮度次序反了（已修）

**观察到的**：`Shell(mvn -q test -Pquick)` 是暗灰，而 `… +103 行 (ctrl+o 查看全部)` 是亮白——一个块里
**最不重要的一行最亮**，用户扫「哪条命令」时那行反而最先跳出来。

**机理**：两半各自看都「对」。调用头走 `BlockHeader.label`，那是 ADR 0013 起就定的暗灰折叠头样式；溢出行
是 `new AttributedString(BlockOverflow.line(n))`，**根本没带样式**，于是拿到终端默认的亮前景色。没有任何
地方**比较**过这两者，所以离线全绿而屏上是反的。

**修法**：亮度按「用户找的是什么」分三档——调用头 `BlockHeader.identity`（普通前景色，它是用户点名要的
那个动作）、思考 / 代码 / diff 头仍 `label`（环境信息）、溢出脚注 `BlockHeader.footnote`（最暗）。文案仍
只有 `BlockOverflow` 一处（D7 不变）。**判据钉的是次序而不是两个样式**
（`ToolCallBlockTest.theCallHeaderReadsBrighterThanTheOverflowFootnote`），因为分开断言正是漏掉它的那种写法。

#### 2. 运行中的[[工具块]]留下副本，[[输入框]]被一起留在里面（**未修**）

**观察到的**（截图）：屏上出现**两个** `Shell(mvn -q test -Pquick)` 头。第一个后面跟着一行告警，然后是
**一行[[输入框]]**——带底纹、右端是 `steer · esc 停止`、左端一个 `…`——再往下才是第二个 `Shell(...)` 头，
带 `命令执行完成 (exit code: 130)` 与完成态结果。

**这正是 ADR 0017 判据针对的那类缺陷，只是发生在 issue 03 的运行尾上而不是 issue 01 的完成块上**：块先在
[[活区]]里画（头 + 运行尾 + 输入框 + 状态坞），完成时提交完成态——而**运行时那几行没有在冻结批写出之前被
擦掉**，于是留成副本。输入框跟着一起留下，是因为它本来就是活区帧的一部分（ADR 0014 决策 2），并不是它自己
跑到转写里去了。

**机理尚未定位，以下是候选而不是结论**（本仓库的规矩：measured vs inferred 要分清）：
`emitPendingScrollback` → `clearLiveRegion()` 靠 `lastRegionRows` 回退光标再擦，这条在 epoch 内成立的前提是
「活区此刻恰好占着 `lastRegionRows` 行、且光标在它底部」。运行尾**会改变活区高度**（尾巴 1→5 行增长，完成
时 5 行尾换成 3 行头，区域收缩），而活区贴在屏幕底部时增长会让**终端自己滚屏**——`lastRegionRows` 记的行数
与它们此刻真正所在的屏幕位置可能不再对应。**这条必须先离线复现再动手**，不要照着这段猜测改。

**离线判据缺口**：issue 03 的 `aFinishedCommandsRunningTailIsGoneFromTheScreen` 是绿的，所以现有屏幕真相
用例**没有覆盖**真机上发生的这个序列。复现要素怀疑是「输出行数远超尾预算 + 活区贴底 + 命令长时间运行」，
现有用例大概都不满足。**先补一条会红的用例，再谈修。**

#### 3. `@` 补全菜单关掉后不清屏，留下残行（**未修**）

**观察到的**（截图）：`> 读取 @` 之后弹出本地路径补全菜单，选中一项后菜单**没有被擦干净**——`本地路径`
标题压在 `rl+Y to enable HITL`（状态坞文字）上，候选行与 Banner / 状态坞交错，同一批候选出现两次。

**大概率不属于 ADR 0017**：补全菜单是 `LineReaderImpl` 自己画进捕获帧的，走的是 ADR 0014 的
`CaptureDisplay` 通路，与工具块 / 结果通路无关。菜单展开时捕获帧**变高**，收起时变矮，多出来的行要由活区
合成时擦掉——这与 issue 03 的运行尾改变活区高度是**同一类**问题（区域高度变化后的擦除），两者可能同源。

**待确认**：在 `58adeab`（输入框那条分支，ADR 0017 一行代码都没有）上是否复现。**这一步必须真机**，因为
问题本身只在真机上被看到过。如果那里也复现，它归 `.scratch/always-live-input-box/` 而不是本 tracker。

### 第二轮，2026-09-01 —— 缺陷 3 已离线复现并已定归属；缺陷 2 搜不到

#### 缺陷 3：**已定位、已修、已换 tracker → `.scratch/always-live-input-box/issues/13-completion-menu-leaves-residue.md`**

上一轮写的「这一步必须真机」**已经不成立**。复现只需要 `InlineRenderer` + 真实 `CafeCliLineReader` +
一个会返回多个候选的 completer，这三样在 `58adeab` 上全都有，所以那句待确认变成了一次离线 bisect。

**离线复现**（真实行编辑器 + 真实补全菜单，`TerminalScreenModel` 判屏）：80×24、6 行转写、24 个候选
（`@candN/some/long/path/FileN.java`）、`AUTO_LIST` 开 `AUTO_MENU` 关；键入 `@cand` → Tab（菜单展开）→
`1` Tab → `x`（菜单收起）。收起后的屏幕：

```
  6 [ 79] |─────────────────────────────────────────────────────────────────────────────── |
  7 [ 80] |> @cand                                                                         |
  8 [ 79] | ──────────────────────────────────────────────────────────────────────────────|  ← 整行右移一列
  9 [ 79] |@cand1/some/long/path/File1.java     @cand20/…                                  |
 10 [ 79] |         el · glm-5.1  idle  ctx ░░░░░░░░ 0% (0/200.0k)  ~/Project/paicli-tui-r|  ← 状态坞文字被压
 19 [ 69] |@cand141some/long/path/File14.java   @cand3/…|                                     ← 候选行被写花
```

菜单收起后仍有 **7 行候选**留在屏上，文档 36 行 / 屏高 24。第 10 行正是真机报的「候选压在
`rl+Y to enable HITL` 上」——同一个症状，同一个形态。

**bisect 结论**：把同一个用例原样搬到 `58adeab` 的 worktree 上跑，残留**逐行相同**（只有状态坞里的 cwd
字符串因 worktree 路径不同而不同）。所以它**不属于本 tracker**，请挪到 `.scratch/always-live-input-box/`。

**机理（已定位并已修，细节在 issue 13）**：`LineReaderImpl.redisplay` 用
`columnSplitLength(columns, **true**, …)` 切显示行，第二个参数是 `includeNewlines`，所以**捕获帧的一行
会把 `'\n'` 留在行尾**（菜单是一整串带内嵌换行的文本）。`InputBoxChrome.washed` 把它一起拷进去，而
`columnLength()` 把 `'\n'` 算作 **−1** 列，于是底纹补齐补在换行**之后**；`hardTerminated` 再补一个，
`Display.update` 只剥掉末尾那一个——**一个「行」占了两个物理行**，活区的行数全部少算，擦除擦不干净。
修法是在 `CaptureDisplay.Frame` 构造期逐行去掉换行。当初记在这里的「整行右移一列 = 延迟折行续行编码」
是**症状不是成因**，与 ADR 0016 那个光标缺陷无关。

**已排除的两条**（都是量出来的，不是推的）：
- `BlockSource.clip` / `ProseEntityHighlighter.wrap` 在双宽边界上**不会**超出列宽（columns 10–20 ×
  前缀 0–4 全扫，一次都没超）。
- `InputBoxChrome.boxWidth` 那条「上界是可见行最大列宽」的豁免**不是**成因：把它硬夹回 `width - 1`
  之后屏幕**逐行不变**，第 7 行仍然是 80 列。也就是说那第 80 列不是我们补出来的。

#### 缺陷 2：400 个随机场景 × 6 种几何量，**复现不出来**

建了一个屏幕真相 fuzz：随机事件脚本（普通文本 / 后台通知 / [[提交块]] / [[转向消息]] / 答案 /
thinking / reasoning / 工具批次开合 / 运行中命令输出 / 输入框高度 1–18 行来回变 / `endTurn`）×
{80×24, 80×20, 80×16, 72×14, 100×30, 80×12}，判据是「每个唯一标记不得出现两次，输入框与状态坞恰好一次，
运行尾一行不留」。**400/400 全绿。**另外单独试过：真实 `CafeCliLineReader`、把[[活区]]顶到屏幕底部
（转写 22 行 / 屏高 24）、40 行输出、取消通知夹在中间、真实补全菜单同框——都干净。

**这个阴性结果是可信的，因为 fuzz 先被验证过有分辨力**（A19 那道疤的纪律）：把
`emitPendingScrollback` 里的 `clearLiveRegion()` 拿掉，**400/400 全红**，报的恰好是真机那个形态——
`toolmark-001 x2, input box x5, dock x2, running tail survived x10`。所以它看得见这一类缺陷，只是
在这些事件序列里**没有**发生。

顺带排除一条：把 `clearLiveRegion` 的光标上退量改成少退一行（人为 off-by-one），产生的是**空行间隙**
而不是副本——所以「擦除距离算错」这一族**不产生**真机报的那个形态，上一轮 Comments 里那个候选机理
（`lastRegionRows` 与屏幕位置不再对应）**在这个方向上得不到支持**。

**因此下一位不必重跑上面这些。**剩下的保真度缺口只有一个：**真实 `InteractiveRepl` + 真实
`RenderLoop` 33ms cadence**（本轮全部用 `ManualFramePump` 同步泵，事件与帧是串行的；真机上
`appendCommandOutput` 是在一帧正在合成的过程中从 `cafecli-command-output` 线程投进来的）。
另一条是缺陷 3 修好之后回来看——两者若真同源，修了 3 说不定 2 就跟着没了。
