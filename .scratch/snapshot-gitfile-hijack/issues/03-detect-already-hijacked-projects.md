# 03 — 已被劫持的项目：检测、停用、修复指引

Status: needs-triage
Type: 判断题（需要用户定方向）
Blocked by: 01

## Parent

`.scratch/snapshot-gitfile-hijack/PRD.md` · ADR 0018

## 问题

01 让 bug 不再**发生**，但对**已经被咬过**的项目无效：它们的 `.git` gitfile 已经指向 `~/.cafecli/snapshots/…`，修复后的 Cafecli 在那个目录里跑，仍然会把快照仓库当成项目仓库。用户看到的还是错的历史。

凡是在 linked worktree 里跑过第 18 期之后任一版本 Cafecli 的人都在这个集合里。集合大小未知。

## ADR 0018 的立场

**检测 + 停用 + 指引，不自动改写。** 理由：从 `gitdir: ~/.cafecli/snapshots/…` 这个指向**推不回**原始 gitdir（`git worktree repair` 必须从主仓库那侧发起，它知道 `worktrees/<name>` 的注册表；被劫持的那侧什么都不知道）。猜错就是第二次静默改写，而这次发生在用户已经知道有问题的时候——比第一次更糟。

## 待定的形状（这就是需要 triage 的部分）

检测本身是确定的：启动时若项目根 `.git` 是 gitfile 且其 `gitdir:` 落在快照根之下，即命中。**命中之后做什么**有三个候选，代价不同：

| 选项 | 行为 | 代价 |
|---|---|---|
| A | 停用快照 + 每次启动一条可读警告 + 打印 `git worktree repair` 指引 | 用户可能一直忽略警告，带着坏 `.git` 继续工作 |
| B | 同 A，但**拒绝启动**直到用户处理 | 对一个我们自己造成的问题，把用户锁在门外 |
| C | 同 A，外加一个显式命令（如 `/snapshot repair`）在用户**明确要求**时尝试修复 | 需要用户提供主仓库路径；实现量最大 |

倾向 A（最小、不越权），但这是产品决定不是技术决定——**请用户定**。

## 若选 A / C，指引文案要说清楚的

修复由用户在**主仓库**那侧发起，不是在被劫持的目录里：

```bash
cd <主仓库>
git worktree repair <被劫持的目录>
git worktree list          # 两个路径都应解析
```

以及一句「你在这个目录里自 <日期> 以来的提交可能在 `~/.cafecli/snapshots/…` 而不是项目仓库里，用 `git --git-dir=<那个路径> log` 查看」——本仓库正是这样把 5 周的工作找回来的。

## 判据

- [ ] 用户已选定 A / B / C
- [ ] 检测不产生误报：`.git` 是目录、是普通 submodule gitfile、指向非快照根的 gitfile，三种情况都不命中
- [ ] 检测本身**不写**任何东西（它是这条 bug 的补救，不能是同一类错误的第二次）
