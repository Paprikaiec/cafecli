# Claude Code agent runtime state

Research date: 2026-10-18. Scope: local `claude-code/` source snapshot at commit `4b9d30f7953273e567a18eb819f4eddd45fcc877` (2026-03-31). The [archive README](../../claude-code/README.md:1) describes an unofficial mirror. This is source analysis of available code, not a claim about current deployed product behavior. Some imported declarations/modules are missing; claims below follow concrete constructors, assignments, and call sites rather than treating comments as guarantees.

## What an agent owns beyond its prompt

An agent's execution state is distributed across a `ToolUseContext`, query-loop locals, the root application store, React refs, module-level registries/caches, and external resources. `ToolUseContext` carries actual tool implementations, live MCP clients, callbacks, file-read state, identity, and cancellation. It is a host-side runtime object; the API request separately serializes messages, system text, tool schemas, and model settings. The whole runtime object is not sent to the model. Sources: [ToolUseContext](../../claude-code/src/Tool.ts:158), [API request construction](../../claude-code/src/services/api/claude.ts:1699).

## Main context and the root store

`getToolUseContext()` reads the store at execution time. It assembles actual tools using the latest permission context and MCP tool set; merges initial MCP clients with the store's clients; assigns resources, thinking/model settings, and agent definitions; and exposes `getAppState: () => store.getState()`. A `refreshTools` callback can recompute available tools mid-query. This is an explicit freshness mechanism, rather than a copied immutable session blob. Source: [REPL.tsx](../../claude-code/src/screens/REPL.tsx:2392).

The root state contains settings, permissions, plugins, MCP state, agent definitions, file history, attribution, tasks, name-to-agent mapping, per-agent todos, UI notifications, elicitation requests, and session hooks. The store holds its current state in a closure and supports subscription. The provider creates the store once and rejects nested providers. Sources: [AppStateStore.ts](../../claude-code/src/state/AppStateStore.ts:89), [runtime portions](../../claude-code/src/state/AppStateStore.ts:158), [store implementation](../../claude-code/src/state/store.ts:10), [provider](../../claude-code/src/state/AppState.tsx:37).

This is selective sharing. `createSubagentContext()` defaults `setAppState` to a no-op and disables most UI mutations, but `getAppState()` still obtains the parent's latest root state, adding a permission-prompt suppression flag. It intentionally keeps the root `setAppStateForTasks` channel and attribution updater. Thus “all mutable state isolated” in the helper's introductory comment should not be read literally as a deep copy of all application state. The assignments establish the actual boundary. Source: [createSubagentContext](../../claude-code/src/utils/forkedAgent.ts:345).

Named Agent execution also differs from a generic background fork. It overrides options and `getAppState`, can adjust the agent's permission view, shares normal app writes for synchronous runs, disables normal writes for async runs, and contributes response metrics in both cases. It still keeps root infrastructure writes through the separate channel. Sources: [root setter](../../claude-code/src/tools/AgentTool/runAgent.ts:332), [permission view](../../claude-code/src/tools/AgentTool/runAgent.ts:416), [context overrides](../../claude-code/src/tools/AgentTool/runAgent.ts:697).

Within `query()`, the system prompt, user/system context parameters, permission callback, source, and limits are bound once rather than reassigned each iteration. In contrast, the local `State` object explicitly carries changing messages, `ToolUseContext`, retry/compaction state, output limits, pending tool summaries, stop-hook state, round count, and transition reason. This execution state is not represented only by message history. Sources: [fixed parameters](../../claude-code/src/query.ts:252), [mutable State](../../claude-code/src/query.ts:203), [ordinary next iteration](../../claude-code/src/query.ts:1714).

There is also async-local identity outside both objects: `runWithAgentContext()` uses `AsyncLocalStorage.run()` for subagent/teammate attribution. The stored metadata includes agent identity, parent/invoking request, spawn/resume kind, and teammate coordination fields. The implementation establishes per-async-chain access; the comment explains that a single shared AppState identity would race between concurrent agents. It also documents environment-variable identity for separate-process teammates, which should not be generalized to the in-process fork path. Sources: [agent context types](../../claude-code/src/utils/agentContext.ts:32), [storage/runner](../../claude-code/src/utils/agentContext.ts:93), [rationale and process distinction](../../claude-code/src/utils/agentContext.ts:13).

## MCP: configuration, connection, tools, and lifecycle

MCP configuration is declarative data: command/args/env or network URL/headers/auth options, plus a configuration scope. A live connection is different: the `connected` variant holds an SDK `Client`, capabilities, server information/instructions, original config, and async cleanup function. Pending, failed, disabled, and needs-auth records are alternative connection states. Sources: [config schemas](../../claude-code/src/services/mcp/types.ts:28), [scoped config](../../claude-code/src/services/mcp/types.ts:163), [connection variants](../../claude-code/src/services/mcp/types.ts:179).

`connectToServer()` constructs the actual transport and SDK client, registers lifecycle cleanup, and memoizes the result by server name plus serialized configuration. Transport/client objects and their listeners remain host-side. Tools/resources/commands are fetched separately and cached. Clearing a server cache cleans up a connected client and invalidates connection and discovery caches. Sources: [cache identity](../../claude-code/src/services/mcp/client.ts:581), [client construction](../../claude-code/src/services/mcp/client.ts:985), [cleanup registration](../../claude-code/src/services/mcp/client.ts:1572), [cache invalidation](../../claude-code/src/services/mcp/client.ts:1648).

The interactive MCP manager maintains root `mcp.clients/tools/commands/resources`, stores reconnection timers in refs, installs handlers for close and tool-list changes, and updates root state. Thus editing MCP configuration, refreshing tool schemas, and owning a live transport are related but separate operations. Sources: [manager state](../../claude-code/src/services/mcp/useManageMCPConnections.ts:143), [connection callback](../../claude-code/src/services/mcp/useManageMCPConnections.ts:293), [root MCP shape](../../claude-code/src/state/AppStateStore.ts:173).

For named Agent children:

- Without an agent `mcpServers` definition, parent clients are returned directly.
- A string reference resolves an existing server configuration and uses the memoized connection factory; the child does not clean up that referenced connection.
- An inline definition receives `scope: dynamic`, is tracked for cleanup, and adds fetched tools to the child's tool set. The child `finally` invokes that cleanup without closing inherited parent connections.

These are concrete branches in [runAgent.ts:95](../../claude-code/src/tools/AgentTool/runAgent.ts:95), [tool merge/options](../../claude-code/src/tools/AgentTool/runAgent.ts:648), and [finally cleanup](../../claude-code/src/tools/AgentTool/runAgent.ts:816). There is a limit to the ownership claim: inline definitions are named `newlyCreated` by the caller, but the connection factory still memoizes by name plus config. The traced code does not guarantee a distinct transport for two concurrent agents using an identical inline definition.

## Hooks: definitions are not executions

Matching combines three inputs: the allowed settings snapshot, globally registered SDK/plugin callbacks, and the current session/agent's dynamically registered hooks. `toolUseContext.agentId ?? getSessionId()` chooses the session-hook bucket. Therefore global configured hooks may apply to many agents while a particular agent's frontmatter hook is scoped to that agent. Matching also enforces managed-hook policies. Sources: [combine sources](../../claude-code/src/utils/hooks.ts:1493), [scope selection](../../claude-code/src/utils/hooks.ts:2001), [snapshot policy](../../claude-code/src/utils/hooks/hooksConfigSnapshot.ts:18).

Session hooks can contain actual in-memory function callbacks, which cannot be serialized to settings JSON. Registration mutates a root-owned Map and returns the previous AppState, deliberately avoiding UI subscriber notification. Named agent frontmatter hooks register into its agent-ID entry, with Stop converted for subagent usage, and are cleared in `finally`. Sources: [function hook](../../claude-code/src/utils/hooks/sessionHooks.ts:14), [Map mutation](../../claude-code/src/utils/hooks/sessionHooks.ts:167), [agent registration](../../claude-code/src/tools/AgentTool/runAgent.ts:557), [agent cleanup](../../claude-code/src/tools/AgentTool/runAgent.ts:819).

Scope and write-channel choice depend on registration site. The inline skill/slash-command path explicitly passes `getSessionId()` and `context.setAppState` to `registerSkillHooks`, rather than the child agent ID and root infrastructure setter used by named agent frontmatter. Therefore the agent-frontmatter rule should not be generalized to every skill registration or every background child. Source: [inline skill registration](../../claude-code/src/utils/processUserInput/processSlashCommand.tsx:869).

An executing async command hook introduces another state object: the process registry holds its `ShellCommand`, timeout/start time, progress cleanup, and response-sent flag. That registry is independent of both declarative hook settings and session-hook registrations. Source: [AsyncHookRegistry.ts](../../claude-code/src/utils/hooks/AsyncHookRegistry.ts:12).

## Tasks, queues, cancellation, and file caches

Tasks are root-owned records with lifecycles; local agents can hold controllers, progress/results, pending inbound messages, retained display transcripts, and cleanup handlers. `registerAsyncAgent()` creates or links a task controller, registers shutdown cleanup, then inserts the task into AppState. Source: [LocalAgentTask registration](../../claude-code/src/tasks/LocalAgentTask/LocalAgentTask.tsx:466).

The unified command queue is a separate singleton for user input and notifications. Priority determines dequeue order. Mid-turn query draining filters commands: main query consumes untargeted commands; subagents consume only task notifications addressed to their own agent ID, never ordinary user prompts. Local-agent SendMessage delivery also uses the task's `pendingMessages` array, with explicit enqueue/drain methods. These are runtime queues until their contents are converted into messages for a future model call. Sources: [queue operations](../../claude-code/src/utils/messageQueueManager.ts:128), [routing](../../claude-code/src/query.ts:1560), [task pending messages](../../claude-code/src/tasks/LocalAgentTask/LocalAgentTask.tsx:162).

Cancellation is caller-specific, so “subagent cancellation is always linked” is inaccurate. The generic fork helper creates a one-way linked child by default. Named agent execution accepts an explicit controller; otherwise sync uses parent and async uses a fresh controller. Task registration can itself create a linked controller if a parent is supplied. Sources: [fork cancellation](../../claude-code/src/utils/forkedAgent.ts:349), [runAgent cancellation](../../claude-code/src/tools/AgentTool/runAgent.ts:525), [task controller](../../claude-code/src/tasks/LocalAgentTask/LocalAgentTask.tsx:485), [one-way helper](../../claude-code/src/utils/abortController.ts:68).

Read-file state is another host-side working memory. It tracks raw disk content, timestamp, read range, and whether an auto-injection exposed only a partial view; it supports read-before-write checks and changed-file detection. It is bounded by entry count and bytes, and child construction clones the cache via dump/load. It is distinct from durable auto memory and from the actual text remaining in a model conversation. Sources: [FileStateCache](../../claude-code/src/utils/fileStateCache.ts:4), [clone](../../claude-code/src/utils/fileStateCache.ts:120), [main lifetime](../../claude-code/src/screens/REPL.tsx:1952).

Finally, process globals remain outside all these context objects: bootstrap session/project/cwd state, connection memoization, callback registries, pending async hook processes, and queue state. A same-process child with isolated conversation history does not receive an isolated copy of the host process or filesystem. The model observes selected projections of this runtime through tool schemas, execution results, and injected attachments. Sources: [bootstrap singleton](../../claude-code/src/bootstrap/state.ts:429), [default options sharing](../../claude-code/src/utils/forkedAgent.ts:444), [API serialization](../../claude-code/src/services/api/claude.ts:1699).
